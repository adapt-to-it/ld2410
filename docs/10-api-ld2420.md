# 10 — API: LD2420 (sibling sensor)

The **LD2420** is a separate 24 GHz radar product in the HLK line — *not*
a variant of LD2410. It shares the wire-level command envelope and LE
byte order with the LD2410 family, but exposes a register-level / ABD-
parameter command vocabulary and reports raw 2DFFT energies rather than
a classified presence/distance pair. Detection policy lives on the host.

This library ships a sibling class `ld2420` alongside `class ld2410`.
You include whichever header(s) your sketch needs — there is no shared
runtime state, no shared instance, and no compile-time variant flag
relating LD2410 and LD2420. They link independently.

> ⚠️ **UNVERIFIED on hardware.** The maintainer's bench does not currently
> have an LD2420 sample. The class compiles for esp32 / esp8266 / rp2040
> and the protocol decoding is transcribed directly from the V2.2 XLSX
> ([`HLK-LD2420_protocol.md`](HLK-LD2420_protocol.md)), but no command
> path is field-measured yet. If you have an LD2420 and find a
> discrepancy, please open an issue.

## Status

This API page tracks the scaffold revision. Only the methods listed
below are exposed. The roadmap of pending commands lives in
[`ld2420-method-coverage.md`](ld2420-method-coverage.md).

## Quick start

```cpp
#include <Arduino.h>
#include <ld2420.h>

ld2420 radar;

void setup() {
    Serial.begin(115200);
    Serial2.begin(115200, SERIAL_8N1, 16, 17);  // your wiring
    radar.debug(Serial);
    if (radar.begin(Serial2)) {
        Serial.print("LD2420 firmware: ");
        Serial.println(radar.firmware_version_ascii);
        Serial.print("protocol version: ");
        Serial.println(radar.protocol_version);
    }
}

void loop() {
    radar.read();  // drains UART → circular buffer → parser
}
```

See [`examples/ld2420_basicSensor`](../examples/ld2420_basicSensor/ld2420_basicSensor.ino)
for the working sketch (compiles on ESP32 / ESP8266 / RP2040).

## Data frame (energy mode)

The LD2420 emits 45-byte energy frames continuously while outside
command mode and configured for per-gate energy output. Each frame
carries:

- a 1-byte **presence** flag from the radar's on-chip ABD classifier,
- the 2-byte **target distance** in centimetres,
- the 16 × 2-byte per-gate **FFT energy** values (squared 2DFFT modulus).

Full layout (head/footer bytes, length field, field offsets) is in
[`HLK-LD2420_data_format.md`](HLK-LD2420_data_format.md).

### `bool presenceDetected()`

The radar's ABD classifier decision. `true` while the on-chip
detection considers a target present.

### `uint16_t targetDistance()`

Most recent target distance in centimetres. Valid only while
`presenceDetected()` is `true`; otherwise may hold stale data from the
last detection.

### `uint16_t gateEnergy(uint8_t gate)`

Squared 2DFFT modulus at the given range gate (0..15). Out-of-range
gate values return `0`. Higher numbers mean more reflected energy;
compare against the per-gate ABD thresholds you configured via
`setAbdHighThresholdAtGate` / `setAbdLowThresholdAtGate` if you want
to second-guess the on-chip classifier.

### `bool dataFrameReceived()`

`true` once any energy frame has been parsed; sticky. Useful for "is
the radar streaming?" checks separate from "did the last command get
an ACK?".

### `void snapshotTargetState(LD2420TargetState & out)`

Atomic snapshot of presence + distance + all 16 gate energies under
`portMUX(data_mux_)` on ESP32. Use this when iterating multiple fields
together — the per-field getters above are NOT atomic against
concurrent `autoReadTask` writes on dual-core ESP32 (caller may
observe a new `presenceDetected()` paired with a previous frame's
`targetDistance()`). On non-ESP32 the lock degenerates to a single
memcpy (single-thread assumption).

```cpp
LD2420TargetState state;
radar.snapshotTargetState(state);
if (state.presence) {
    Serial.print("target @ ");
    Serial.print(state.distance_cm);
    Serial.print(" cm, gate 4 energy: ");
    Serial.println(state.gate_energies[4]);
}
```

## Lifecycle

### `bool begin(Stream & uart, bool waitForRadar = true)`

Bind the radar UART. With `waitForRadar = true` (default) the method
calls `requestFirmwareVersion()` repeatedly for up to 1 s and returns
`true` only when the radar ACKs. Pass `false` to skip the probe — useful
when the radar may boot later than the host.

### `void debug(Stream & terminal)`

Tee the driver's debug output to a second stream (typically `Serial`).
Compile-time gated by `LD2420_DEBUG_COMMANDS` (verbose) — define before
`#include <ld2420.h>` to enable.

### `bool isConnected()`

`true` if a frame (any kind) was parsed within the last
`radar_uart_timeout` ms (= 100 ms default).

### `bool read()`

Drain pending UART bytes into the circular buffer, then advance the
parser by one frame. Returns `true` if a complete frame was parsed this
call. Safe to call from `loop()` at any cadence.

### `bool autoReadTask(stack, priority, core)` *(ESP32 only)*

Spawn a FreeRTOS task that calls `read()` continuously. Same pattern as
`ld2410::autoReadTask()`. Stop with `stopAutoReadTask()`; query with
`isAutoReadTaskRunning()`.

## Command mode

The LD2420 emits waveform data by default; **any other command issued
without first entering command mode is invalid** (HLK §1.1.1).
Configuration-mutating helpers wrap themselves in enter/exit pairs
automatically; call these directly only when batching multiple commands
under a single open/close.

### `bool enterCommandMode()`

Implements the two-step "double tap" required by §1.1.1: sends the
0x00FF open command twice with a 100 ms cache-clear delay between, so
in-flight waveform bytes do not contaminate the ACK. On success
populates:

- `uint16_t protocol_version`  — currently `2` for V2.2 firmware.
- `uint16_t tx_rx_buffer_size` — radar's command-mode buffer, e.g.
  `0x0400` = 1024 bytes on production firmware.

### `bool exitCommandMode()`

Sends 0x00FE; on success the radar resumes waveform output.

## Register r/w (0x0001 / 0x0002)

Single-register access. The protocol allows bulk operations but the
public API exposes only the single-register path — bulk can be added
later if a real use case needs it.

### `bool writeRegister(uint16_t chip, uint16_t reg, uint16_t value)`

Writes `value` to register `reg` on chip `chip`. Returns `true` on
success. Wraps its own `enterCommandMode()` / `exitCommandMode()`
pair — call directly from user code.

### `bool readRegister(uint16_t chip, uint16_t reg, uint16_t & out)`

Reads register `reg` on chip `chip` and stores the 2-byte value in
`out`. Returns `true` on success; `out` is left unchanged on failure.

> Wire-protocol note: the V2.2 XLSX "Read register" send-frame examples
> print the intra-length field two bytes short of the actual body size.
> Every other send example and every receive example uses the
> consistent convention `len = full intra including cmd-word`, and
> that is what the firmware on the wire accepts. The driver follows
> the consistent convention.

## ABD parameters (0x0007 / 0x0008)

"ABD" = Adaptive Background Detection — the per-gate threshold system
the LD2420 uses to classify FFT energies into a presence decision.
There are TWO independent threshold blocks (high and low) each with
its own active/inactive frame counts and per-gate threshold values,
plus three global parameters (`roiMin`, `roiMax`, `delayTime`).

> Asymmetric vocabulary: the WRITE words (`LD2420_ABD_W_*`) treat
> `roiMin`/`roiMax`/`delayTime` as global parameters, but the READ
> words (`LD2420_ABD_R_*`) report them per high/low block — so reading
> back a global write yields two values where the write only set one.
> The driver exposes both vocabularies verbatim; convenience helpers
> use the global write words.

### Low-level

```cpp
bool writeAbdParameter(uint16_t word, uint32_t value);
bool readAbdParameter (uint16_t word, uint32_t & out);
```

Use these with the `LD2420_ABD_W_*` and `LD2420_ABD_R_*` constants from
`src/ld2420_variants/ld2420_v22.h` when you need fine-grained control.

### Global ROI

```cpp
bool setAbdRoi(uint16_t min_gate, uint16_t max_gate);
```

Writes `LD2420_ABD_W_ROI_MIN` and `LD2420_ABD_W_ROI_MAX` in a single
0x0007 frame (one command-mode roundtrip instead of two).

### Per-gate thresholds

```cpp
bool setAbdHighThresholdAtGate(uint16_t gate, uint16_t threshold);
bool setAbdLowThresholdAtGate (uint16_t gate, uint16_t threshold);
bool readAbdHighThresholdAtGate(uint16_t gate, uint16_t & out);
bool readAbdLowThresholdAtGate (uint16_t gate, uint16_t & out);
```

The 0x0012 / 0x0022 write words use a packed 4-byte value:

```
bits [15:0]   = gate index (0..15)
bits [31:16]  = threshold value
```

The §1.2.4 example for gate 5, threshold `0x1234` sends `05 00 34 12`
on the wire (uint32_t `0x12340005`). The `set*ThresholdAtGate` helpers
do the packing for you.

The read side does NOT use the packing — the radar replies with the
4-byte threshold value only, and the helpers narrow to `uint16_t` for
the caller.

```cpp
// Tighten high-threshold at gate 4 to 0x1500
radar.setAbdHighThresholdAtGate(4, 0x1500);

// Read it back
uint16_t thresh = 0;
if (radar.readAbdHighThresholdAtGate(4, thresh)) {
    Serial.printf("gate 4 high threshold = 0x%04X\n", thresh);
}
```

## System parameters (0x0012 / 0x0013)

The LD2420 exposes three "system parameter" words (HLK §1.2.7 Table 7):
`LD2420_SYS_W_MODE`, `LD2420_SYS_W_UPLOAD_SAMPLE_RATE`,
`LD2420_SYS_W_DEBUG_MODE`. The first one is the only one most users
ever touch; the other two are vendor-internal.

### `bool writeSystemParameter(uint16_t word, uint32_t value)` / `bool readSystemParameter(uint16_t word, uint32_t & out)`

Generic single-word access. Each parameter is a 4-byte little-endian
value on the wire.

### `bool setSystemMode(uint8_t mode)` / `bool getSystemMode(uint8_t & out)`

Convenience wrappers around `LD2420_SYS_W_MODE`. Mode values:

| Constant | Value | Description |
|---|---|---|
| `LD2420_SYS_MODE_TRANSPARENT` | 0 | Transparent — raw FFT output. |
| `LD2420_SYS_MODE_MTT` | 1 | Multi-target tracking. |
| `LD2420_SYS_MODE_VS` | 2 | VS mode. |
| `LD2420_SYS_MODE_GR` | 3 | GR mode. |
| `LD2420_SYS_MODE_CUSTOM_BASE`+ | ≥10 | User-defined custom modes. |

```cpp
uint8_t mode = 0;
if (radar.getSystemMode(mode)) {
    Serial.print("current mode: ");
    Serial.println(mode);
}
radar.setSystemMode(LD2420_SYS_MODE_MTT);
```

## Serial number (0x0011)

### `bool requestSerialNumber()`

Reads the module identifier (uint16_t) and the 4-byte serial number.
On success populates:

- `uint16_t module_identification`
- `uint32_t serial_number`

```cpp
if (radar.requestSerialNumber()) {
    Serial.printf("module 0x%04X, SN %u\n",
                  radar.module_identification, radar.serial_number);
}
```

## Factory test mode (0x0024 / 0x0025 / 0x0026)

Three commands behind the radar's factory-test mode. Useful when
checking the firmware-configured chirp parameters or for the
register-update path (`sendFactoryTestResult`); rarely needed in
normal application code.

### `bool enterFactoryTestMode()`

Sends 0x0024. The ACK carries the 14-byte metadata block from HLK
Table 8; on success populates these public fields:

| Field | Width | Meaning |
|---|---|---|
| `ft_subboard_model` | uint16_t | Reserved by HLK; usually 0. |
| `ft_cascaded_chips` | uint16_t | `1` single, `2` dual, … |
| `ft_rx_channels` | uint16_t | Number of receive channels. |
| `ft_data_type` | uint16_t | `LD2420_FT_DATA_TYPE_1DFFT` / `_2DFFT` / `_2DFFT_PEAK` / `_DSRAW`. |
| `ft_1dfft_size` | uint16_t | 1DFFT bin count. |
| `ft_chirps_per_frame` | uint16_t | Chirps per radar frame. |
| `ft_downsampling` | uint16_t | `1` = no downsampling. |

### `bool exitFactoryTestMode()`

Sends 0x0025. No response payload.

### `bool sendFactoryTestResult(uint16_t address, uint16_t data)`

Sends 0x0026 with a single `(address, data)` pair. Per the XLSX, this
"mainly updates the TX register" — a niche but documented path. The
bulk variant (multiple pairs per frame) is not yet exposed.

## Firmware version

### `bool requestFirmwareVersion()`

Sends 0x0000. ACK payload is a 2-byte LE length field followed by an
ASCII version string. On success populates:

- `char firmware_version_ascii[16]` — NUL-terminated copy of the radar's
  version string (the §1.2.1 example shows `"v1.4.14"` — 7 bytes).
- `uint16_t firmware_version_length` — raw byte count reported by the
  radar (excluding the NUL).
- `uint16_t firmware_major_version` / `firmware_minor_version` /
  `firmware_patch_version` — best-effort numeric breakdown parsed from
  the ASCII (leading `v` is skipped; digits split on `.`).

The numeric fields are convenience copies. Trust the ASCII string for
anything load-bearing.

## Concurrency

On ESP32, every `request*` / `set*` helper takes a per-instance command
mutex via the `CommandTransaction` RAII guard. Two FreeRTOS tasks
calling driver methods simultaneously serialise; the second blocks up
to 1 s and returns `false` from the public method if the lock can't be
acquired in time. On other platforms the lock degenerates to a no-op
(single-thread assumption — no FreeRTOS scheduler).

The data-state fields (`firmware_version_ascii`, `protocol_version`,
etc.) are written under `portMUX(data_mux_)` on ESP32, so reading them
from the user loop core while `autoReadTask()` runs on a different core
is safe.

## Build flags

Define before `#include <ld2420.h>`:

| Flag | Effect |
|---|---|
| `LD2420_DEBUG_COMMANDS` | Log every command sent + ACK received on the debug stream (when `debug()` is also wired). |
| `LD2420_DEBUG_DATA` | Log every parsed energy frame (presence + distance) on the debug stream. |
| `LD2420_DEBUG_PARSE` | Reserved — no byte-level parser tracing yet. |
| `LD2420_DEBUG` | Meta-flag — turns on all three above. |
| `LD2420_MAX_FRAME_LENGTH` | Override per-frame buffer (default 96 B). |
| `LD2420_BUFFER_SIZE` | Override circular buffer size (default `4 × LD2420_MAX_FRAME_LENGTH`). |

## What's not here yet

- Non-energy data-frame modes (raw 1DFFT, 2DFFT, 2DFFT peak, DSRAW —
  selectable via the factory-test command's data-type field). The
  current parser handles only the 45-byte energy frame (per-gate
  energies + presence + distance), which is what the on-chip ABD
  classifier needs and what most user code wants.
- Bulk variants of register / system-param / ABD-param r/w, and the
  bulk send-factory-results path (multiple (address, data) pairs in
  one frame).
- Host parser unit test (`tests/test_parser_ld2420/`). Until this
  lands, the data-frame parser is verified by code review + ESPHome
  cross-check only, not by automated tests.
- Hardware validation — no LD2420 on the maintainer's bench yet.

See [`ld2420-method-coverage.md`](ld2420-method-coverage.md) for the
authoritative matrix and roadmap.
